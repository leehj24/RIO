# 한눈에 보기

A-MEM은 단순히 과거 대화를 벡터 데이터베이스에 넣고 비슷한 내용을 검색하는 시스템이 아니다.

새로운 경험이 들어올 때마다 다음 작업을 수행한다.

```text
새로운 상호작용
   ↓
1. 원자적 메모리 노트 생성
   ├─ 원문
   ├─ 시간
   ├─ 키워드
   ├─ 태그
   ├─ 문맥 설명
   └─ 통합 임베딩
   ↓
2. 기존 메모리에서 유사 후보 Top-k 검색
   ↓
3. LLM이 후보들과 실제로 연결할지 판단
   ↓
4. 새 메모리와 기존 메모리 사이에 링크 생성
   ↓
5. 새 경험에 맞춰 기존 메모리의 문맥·키워드·태그 진화
   ↓
6. 질문이 들어오면 관련 메모리를 검색해 응답에 제공
```

핵심은 **기억의 내용뿐 아니라 기억을 조직하는 구조도 동적으로 바뀐다**는 점이다.

기존 RAG는 보통 다음과 같다.

```text
문서 청크 저장
  → 임베딩
  → 질의와 비슷한 청크 검색
  → LLM에 전달
```

A-MEM은 여기에 다음을 추가한다.

```text
기억마다 의미 설명·키워드·태그를 생성
  → 관련 기억끼리 링크
  → 새로운 기억이 들어오면 과거 기억의 해석도 갱신
```

즉, 저장소를 정적인 자료창고가 아니라 **스스로 정리되고 재해석되는 기억 네트워크**로 만든다.

# 해결하려는 문제

## 기존 메모리 시스템의 고정성

일반적인 LLM 에이전트 메모리는 개발자가 다음 사항을 미리 정한다.

- 어떤 데이터를 저장할지
- 언제 저장할지
- 어떤 필드로 저장할지
- 언제 검색할지
- 몇 개를 검색할지
- 기억 사이에 어떤 관계를 허용할지
- 새 정보와 과거 정보가 충돌하면 어떻게 처리할지

예를 들어 다음 구조는 사전에 고정되어 있다.

```json
{
  "user_name": "...",
  "preference": "...",
  "last_task": "...",
  "summary": "..."
}
```

새로운 종류의 관계가 나타나더라도 미리 만든 슬롯 안에만 넣어야 한다.

그래프 데이터베이스를 사용해도 관계 타입이 다음처럼 고정돼 있다면 구조의 자율성은 제한된다.

```text
USER --LIKES--> PRODUCT
USER --WORKS_AT--> COMPANY
EVENT --OCCURRED_AT--> LOCATION
```

A-MEM은 관계 타입을 먼저 고정하지 않고, 메모리의 내용·문맥·유사성을 LLM이 분석해 연결과 재구성을 결정한다.

## 검색 단계만 자율적인 Agentic RAG와의 차이

Agentic RAG는 다음 작업을 자율화한다.

- 검색이 필요한지 판단
- 검색어 재작성
- 여러 번 재검색
- 검색결과 평가
- 답변에 사용할 문서 선택

하지만 지식베이스 자체는 대체로 정적이다.

A-MEM은 자율성을 저장·조직 단계까지 확장한다.

| 구분 | 일반 RAG | Agentic RAG | A-MEM |
| --- | --- | --- | --- |
| 저장 단위 | 문서 청크 | 문서 청크 | 원자적 메모리 노트 |
| 검색 | 벡터 유사도 | 에이전트가 검색전략 결정 | 벡터 검색 + 연결구조 활용 |
| 메타데이터 | 사전 정의 | 사전 정의 | LLM이 키워드·태그·문맥 생성 |
| 기억 간 링크 | 없거나 고정 스키마 | 대체로 고정 | 내용에 따라 동적 생성 |
| 과거 기억 수정 | 일반적으로 없음 | 일반적으로 없음 | 새 경험에 따라 문맥·태그 진화 |
| 구조의 자율성 | 낮음 | 검색 단계에서 중간 | 저장·연결·진화 단계에서 높음 |

# 제텔카스텐에서 가져온 원리

제텔카스텐은 하나의 긴 문서에 모든 지식을 적는 대신, 하나의 아이디어를 하나의 노트로 만들고 관련 노트끼리 연결하는 지식관리 방식이다.

A-MEM은 다음 원칙을 차용한다.

## 원자성

하나의 메모리는 가능한 한 하나의 독립적인 경험이나 사실을 담는다.

```text
나쁜 예:
- 사용자의 취미, 회사, 여행, 식습관을 한 노트에 모두 기록

좋은 예:
- 사용자는 필름 사진을 좋아한다.
- 사용자는 매주 월요일 오전 회의를 한다.
- 사용자는 카페인이 없는 음료를 선호한다.
```

다만 논문은 긴 대화를 실제로 어떻게 원자 단위로 분할하는지 구체적인 세분화 알고리즘을 제시하지 않는다. 구현 시 대화 턴을 그대로 노트로 만들지, 문장·사건·사실 단위로 쪼갤지 별도로 설계해야 한다.

## 유연한 연결

하나의 노트는 여러 주제 그룹에 동시에 속할 수 있다.

```text
"사용자가 여행에서 필름 카메라로 야경을 찍었다."

연결 가능한 의미 그룹:
  ├─ 사진 취미
  ├─ 여행 기록
  ├─ 선호 장비
  └─ 야간 활동
```

논문의 그림 2에서 사용하는 `box`는 물리적인 단일 폴더라기보다 비슷한 문맥을 공유하는 연결집단을 뜻한다. 하나의 메모리가 여러 box에 동시에 포함될 수 있다.

## 점진적 재해석

새로운 경험은 기존 기억의 의미를 바꿀 수 있다.

```text
기존 메모리:
"사용자는 매주 월요일 아침 카페에서 회의한다."

새 메모리:
"지난 월요일 카페가 휴무여서 사무실에서 회의했다."

진화된 문맥:
"사용자는 월요일 아침 정기회의를 하지만 장소는 상황에 따라 달라진다."
```

A-MEM은 과거 원문을 단순 덮어쓰기보다는 문맥 설명·키워드·태그를 새로운 경험에 맞춰 수정하는 방식으로 이를 구현한다.

# 전체 아키텍처

```text
환경·사용자와의 상호작용
            ↓
┌────────────────────────────────────┐
│ 1. Note Construction               │
│                                    │
│ 원문 + 시간                         │
│   → LLM 키워드 생성                 │
│   → LLM 태그 생성                   │
│   → LLM 문맥 설명 생성              │
│   → 통합 임베딩 생성                │
└────────────────────────────────────┘
            ↓
┌────────────────────────────────────┐
│ 2. Candidate Retrieval             │
│                                    │
│ 새 노트 임베딩과 기존 노트의        │
│ cosine similarity 계산             │
│   → Top-k 후보 추출                 │
└────────────────────────────────────┘
            ↓
┌────────────────────────────────────┐
│ 3. Link Generation                 │
│                                    │
│ LLM이 새 노트와 후보 노트 사이의    │
│ 실제 의미·인과·주제 관계 판단       │
│   → 링크 생성 또는 미생성           │
└────────────────────────────────────┘
            ↓
┌────────────────────────────────────┐
│ 4. Memory Evolution                │
│                                    │
│ 새 메모리로 인해 과거 노트의        │
│ context·keywords·tags를             │
│ 수정할 필요가 있는지 판단           │
└────────────────────────────────────┘
            ↓
          저장
            ↓
현재 질문
  → 질의 임베딩
  → 관련 메모리 Top-k
  → 필요 시 연결된 기억 확장
  → LLM 응답 컨텍스트
```

# 메모리 노트의 수학적 정의

논문에서 메모리 집합은 다음과 같다.

\[
\mathcal{M}=\{m_1,m_2,\ldots,m_N\}
\]

각 메모리 노트 \(m_i\)는 다음 속성을 갖는다.

\[
m_i=
\{c_i,t_i,K_i,G_i,X_i,e_i,L_i\}
\tag{1}
\]

각 항목의 의미는 다음과 같다.

| 기호 | 의미 | 예시 |
| --- | --- | --- |
| \(c_i\) | 원래 상호작용 내용 | “요즘 필름 사진을 배우고 있어.” |
| \(t_i\) | 상호작용 시각 | 2025-10-08 13:30 |
| \(K_i\) | LLM이 생성한 키워드 | photography, film, hobby |
| \(G_i\) | LLM이 생성한 태그 | 취미, 창작, 개인성장 |
| \(X_i\) | LLM이 생성한 문맥 설명 | 사용자가 새로운 사진 취미를 시작한 경험 |
| \(e_i\) | 노트 전체의 임베딩 | 384차원 벡터 |
| \(L_i\) | 연결된 메모리 집합 | \(\{m_7,m_{15}\}\) |

논문은 메모리의 원문과 자동 생성된 의미표현을 분리한다.

```text
원본 정보:
  content, timestamp

파생 정보:
  keywords, tags, contextual description, embedding, links
```

실제 구현에서는 원본 정보는 불변으로 보존하고, 파생 정보만 버전별로 갱신하는 것이 안전하다.

# 1. 노트 생성

## 키워드·태그·문맥 설명 생성

새로운 상호작용 내용 \(c_i\), 시각 \(t_i\), 노트 생성 프롬프트 \(P_{s1}\)을 LLM에 입력한다.

\[
K_i,G_i,X_i
\leftarrow
LLM(c_i\parallel t_i\parallel P_{s1})
\tag{2}
\]

여기서 \(\parallel\)은 여러 입력을 이어 붙이는 것을 의미한다.

### 논문의 프롬프트가 요구하는 출력

```json
{
  "keywords": [
    "구체적인 핵심 개념",
    "중요도 순 키워드"
  ],
  "context": "주제, 핵심 주장, 목적을 한 문장으로 요약",
  "tags": [
    "넓은 분류 주제",
    "도메인",
    "콘텐츠 형식"
  ]
}
```

키워드는 구체적인 용어, 태그는 더 넓은 분류라는 차이가 있다.

```text
원문:
"Python으로 주식 가격의 이동평균을 계산했다."

keywords:
  Python, stock price, moving average

tags:
  programming, quantitative finance, technical analysis

context:
  Python을 사용해 주식가격의 이동평균을 계산하는 기술적 분석 작업
```

## 통합 임베딩

원문만 임베딩하지 않고 원문·키워드·태그·문맥 설명을 모두 연결해 임베딩한다.

\[
e_i
=
f_{\mathrm{enc}}
\left[
\operatorname{concat}
(c_i,K_i,G_i,X_i)
\right]
\tag{3}
\]

논문 실험에서는 `all-MiniLM-L6-v2`를 사용한다.

이 모델의 일반적인 임베딩 차원은 384차원이다.

### 원문만 임베딩하는 방식과의 차이

```text
원문 임베딩:
"다음 달에는 부산에 갈 거야."

통합 임베딩:
원문: 다음 달에는 부산에 갈 거야.
키워드: 부산, 여행, 다음 달
태그: 여행계획, 일정, 국내여행
문맥: 사용자가 다음 달 부산여행을 계획하고 있음
```

통합 임베딩은 짧거나 모호한 원문에 LLM이 해석한 문맥을 추가하므로 검색 가능성이 높아질 수 있다.

반대로 LLM의 해석이 틀리면 잘못된 의미가 임베딩에 강하게 반영될 수 있다.

# 2. 링크 후보 검색

새 메모리 \(m_n\)의 임베딩 \(e_n\)과 기존 메모리 \(m_j\)의 임베딩 \(e_j\) 사이에 코사인 유사도를 계산한다.

\[
s_{n,j}
=
\frac{
e_n\cdot e_j
}{
\|e_n\|\|e_j\|
}
\tag{4}
\]

코사인 유사도는 두 벡터의 방향이 얼마나 비슷한지 측정한다.

- \(1\): 매우 유사한 방향
- \(0\): 직교, 관련성이 낮음
- \(-1\): 반대 방향

실제 문장 임베딩에서는 대체로 양수 범위가 많이 나온다.

## Top-k 후보 집합

전체 기존 메모리에서 유사도가 높은 상위 \(k\)개를 가져온다.

\[
\mathcal{M}^{n}_{\mathrm{near}}
=
\{
m_j
\mid
\operatorname{rank}(s_{n,j})\leq k,
m_j\in\mathcal{M}
\}
\tag{5}
\]

이 단계의 후보는 링크가 확정된 것이 아니다.

```text
벡터 검색:
"이 메모리들이 의미상 가까워 보인다."

LLM 링크 판단:
"가까워 보이는 메모리 중 실제로 연결할 만한 것은 무엇인가?"
```

벡터 검색으로 전체 메모리와 LLM을 하나씩 비교하는 비용을 줄인다.

# 3. 링크 생성

Top-k 후보와 새 메모리를 LLM에 전달한다.

\[
L_n
\leftarrow
LLM
\left(
m_n
\parallel
\mathcal{M}^{n}_{\mathrm{near}}
\parallel
P_{s2}
\right)
\tag{6}
\]

논문 본문의 식은 \(L_i\)를 갱신하는 것처럼 표기돼 있지만 문맥상 새 메모리 \(m_n\)의 링크 집합 \(L_n\)을 생성하는 단계로 이해하는 것이 자연스럽다.

링크는 다음처럼 여러 메모리를 묶는 집합으로 설명된다.

\[
L_i=\{m_a,\ldots,m_k\}
\]

## 임베딩 유사도만 사용하지 않는 이유

임베딩이 비슷하더라도 실제 관계는 다를 수 있다.

```text
메모리 A:
"사용자는 Java를 배우고 있다."

메모리 B:
"인도네시아 자바섬에 여행했다."
```

문자열과 일부 임베딩 특징은 가까울 수 있지만 의미는 다르다.

반대로 단어가 달라도 인과적으로 연결될 수 있다.

```text
메모리 A:
"사용자의 회사가 재택근무를 시작했다."

메모리 B:
"사용자가 모니터를 새로 구매했다."
```

LLM은 두 기억 사이에 `재택근무 환경 구축`이라는 암묵적인 관계를 찾을 수 있다.

# 4. 메모리 진화

링크를 생성한 뒤, 새 메모리가 기존 기억의 문맥을 바꾸는지 판단한다.

후보 메모리 \(m_j\)의 진화 결과 \(m_j^*\)는 다음과 같다.

\[
m_j^*
\leftarrow
LLM
\left(
m_n
\parallel
\mathcal{M}^{n}_{\mathrm{near}}\setminus m_j
\parallel
m_j
\parallel
P_{s3}
\right)
\tag{7}
\]

진화된 메모리 \(m_j^*\)는 기존 \(m_j\)를 대체한다.

프롬프트는 다음 행동을 요청한다.

- 연결 강화
- 이웃 메모리 갱신
- 태그 갱신
- 문맥 설명 갱신
- 연결 병합
- 필요 없는 연결 정리

출력 예시는 다음 구조다.

```json
{
  "should_evolve": true,
  "actions": [
    "strengthen",
    "merge",
    "prune"
  ],
  "suggested_connections": [
    "mem-12",
    "mem-41"
  ],
  "tags_to_update": [
    "photography",
    "travel"
  ],
  "new_context_neighborhood": [
    "사용자의 여행과 사진활동이 결합된 경험"
  ],
  "new_tags_neighborhood": [
    [
      "hobby",
      "travel",
      "creative activity"
    ]
  ]
}
```

## 메모리 진화가 필요한 이유

시간순으로 다음 메모리가 추가된다고 가정한다.

```text
m1:
"사용자는 운동을 싫어한다."

m2:
"사용자는 최근 재활을 위해 수영을 시작했다."

m3:
"사용자는 수영을 계속하면서 운동에 흥미가 생겼다."
```

단순 저장만 하면 상충하는 세 문장이 그대로 남는다.

A-MEM은 과거 기억의 문맥을 다음처럼 바꿀 수 있다.

```text
m1의 진화된 context:
"사용자는 과거 운동을 선호하지 않았으나,
재활 목적의 수영을 계기로 태도가 변화하기 시작했다."
```

이렇게 하면 질문 시 최신 상태와 변화 과정 모두를 더 잘 반영할 수 있다.

## 진화 과정의 위험

진화는 강력하지만 다음 위험이 있다.

### 원본 소실

과거 해석을 새 해석으로 덮어쓰면 최초 발언이 사라질 수 있다.

### 기억 드리프트

LLM이 기억을 여러 차례 재작성할수록 원래 사실에서 멀어질 수 있다.

```text
원문:
"사용자는 한 번 등산을 갔다."

1차 진화:
"사용자는 야외활동에 관심이 있다."

2차 진화:
"사용자는 등산을 즐긴다."

3차 진화:
"사용자는 정기적으로 등산한다."
```

원문이 지지하지 않는 성향으로 확대될 수 있다.

### 순환적 자기강화

잘못 생성된 태그나 문맥이 임베딩에 포함되고, 그 임베딩이 다시 잘못된 이웃을 검색해 오류가 강화될 수 있다.

# 5. 관련 메모리 검색

질문 \(q\)가 들어오면 같은 임베딩 모델로 질의 벡터를 생성한다.

\[
e_q=f_{\mathrm{enc}}(q)
\tag{8}
\]

각 메모리와 코사인 유사도를 계산한다.

\[
s_{q,i}
=
\frac{
e_q\cdot e_i
}{
\|e_q\|\|e_i\|
},
\qquad
e_i\in m_i
\tag{9}
\]

상위 \(k\)개 메모리를 검색한다.

\[
\mathcal{M}_{\mathrm{retrieved}}
=
\{
m_i
\mid
\operatorname{rank}(s_{q,i})\leq k,
m_i\in\mathcal{M}
\}
\tag{10}
\]

검색된 메모리를 현재 질문과 함께 LLM에 넣는다.

```text
현재 질문
  + 관련 메모리 Top-k
  → LLM 답변
```

## 연결 그래프 확장에 관한 원문 내부의 모호함

논문의 그림 2 설명은 검색된 메모리와 같은 `box`에 연결된 다른 메모리도 자동으로 접근한다고 설명한다.

```text
질의
  → Top-k 메모리
  → 연결된 같은 box 메모리까지 확장
```

그러나 본문의 공식 (8)~(10)은 코사인 유사도 Top-k 검색만 정의한다. 링크를 몇 hop 따라가는지, 연결된 메모리를 몇 개 추가하는지, 검색점수와 링크점수를 어떻게 결합하는지는 수식으로 제시하지 않는다.

따라서 재현 시 다음 중 어떤 방법을 썼는지 확인해야 한다.

```text
A. 순수 Top-k 벡터 검색
B. Top-k 검색 후 1-hop 링크 확장
C. Top-k 검색 후 같은 box 전체 확장
D. 벡터 점수와 그래프 점수의 결합
```

실제 구현 예시는 다음처럼 만들 수 있다.

\[
Score(m_i)
=
\lambda s_{q,i}
+
(1-\lambda)g_{q,i}
\]

- \(s_{q,i}\): 질의-메모리 임베딩 유사도
- \(g_{q,i}\): 검색된 seed 메모리와의 그래프 연결점수
- \(\lambda\): 두 점수의 비중

이 식은 논문에 직접 제시된 공식이 아니라, 링크 구조를 검색에 반영하기 위한 확장안이다.

# A-MEM 저장·검색 알고리즘

## 메모리 추가

```python
def add_memory(content: str, timestamp: str) -> str:
    # 1. 새 노트의 의미 속성 생성
    metadata = llm_construct_note(
        content=content,
        timestamp=timestamp,
    )

    # 2. 원문과 자동 생성 속성을 통합해 임베딩
    embedding = encoder.encode(
        content
        + " ".join(metadata["keywords"])
        + " ".join(metadata["tags"])
        + metadata["context"]
    )

    new_memory = {
        "content": content,
        "timestamp": timestamp,
        "keywords": metadata["keywords"],
        "tags": metadata["tags"],
        "context": metadata["context"],
        "embedding": embedding,
        "links": [],
    }

    # 3. 유사한 기존 메모리 후보 검색
    neighbors = vector_store.search(embedding, k=10)

    # 4. LLM이 의미 있는 링크를 선택
    link_decision = llm_generate_links(
        new_memory=new_memory,
        neighbors=neighbors,
    )

    new_memory["links"] = link_decision["memory_ids"]

    # 5. 기존 메모리의 파생속성 진화
    evolution = llm_evolve_memories(
        new_memory=new_memory,
        neighbors=neighbors,
    )

    for update in evolution:
        memory_store.append_derived_version(
            memory_id=update["memory_id"],
            context=update["context"],
            tags=update["tags"],
        )

    # 6. 새 메모리 저장
    return memory_store.insert(new_memory)
```

## 메모리 검색

```python
def retrieve_memories(query: str, k: int = 10) -> list[dict]:
    query_embedding = encoder.encode(query)

    seeds = vector_store.search(
        query_embedding,
        k=k,
    )

    # 논문의 그림을 실제로 구현한다면 링크 확장 가능
    linked = graph_store.expand(
        seed_ids=[m["id"] for m in seeds],
        max_hops=1,
        max_nodes=k,
    )

    candidates = deduplicate(seeds + linked)

    return rerank(
        query=query,
        memories=candidates,
        top_k=k,
    )
```

# 계산 복잡도

메모리 수를 \(N\), 임베딩 차원을 \(d\), 후보 검색 수를 \(k\)라고 하자.

## 저장공간

각 메모리가 임베딩과 메타데이터를 하나씩 가진다면 기본 저장공간은 다음과 같다.

\[
O(Nd)
\]

링크 수를 \(E\)라고 하면 전체 메모리 네트워크 저장공간은 더 정확히 다음과 같다.

\[
O(Nd+E)
\]

논문은 세 시스템의 메모리 사용량이 동일한 선형 \(O(N)\)이라고 설명한다. 그러나 A-MEM은 키워드·태그·문맥·링크를 추가하므로 실제 운영환경에서는 단순 원문·벡터만 저장하는 시스템보다 부가 저장공간이 발생한다.

링크가 희소하면 \(E=O(N)\)이므로 전체는 여전히 선형이다. 모든 메모리가 다수의 메모리와 연결되는 밀집 그래프라면 최악의 경우 다음까지 커질 수 있다.

\[
E=O(N^2)
\]

링크 수 제한과 오래된 링크 정리가 필요하다.

## 정확한 전수 벡터 검색

모든 메모리와 코사인 유사도를 직접 계산하면 다음과 같다.

\[
O(Nd)
\]

# 평가 지표 계산법

## F1 Score

정답 토큰 집합과 예측 토큰 집합의 정밀도와 재현율을 조화평균한다.

\[
Precision
=
\frac{
|\mathrm{Prediction}\cap\mathrm{Reference}|
}{
|\mathrm{Prediction}|
}
\]

\[
Recall
=
\frac{
|\mathrm{Prediction}\cap\mathrm{Reference}|
}{
|\mathrm{Reference}|
}
\]

\[
F1
=
\frac{
2\cdot Precision\cdot Recall
}{
Precision+Recall
}
\]

예를 들어 정답이 다음과 같다고 하자.

```text
Reference:
"film photography"

Prediction:
"photography"
```

정확한 토큰 정규화 방식에 따라 다르지만 공통 토큰은 하나이므로 완전일치보다 낮은 F1이 나온다.

## BLEU-1

예측문장에서 정답과 겹치는 unigram 비율을 중심으로 평가한다.

\[
P_1
=
\frac{
\text{일치하는 1-gram 수}
}{
\text{예측문의 1-gram 수}
}
\]

짧은 답변은 단어 하나의 차이에도 점수가 크게 흔들릴 수 있다.

## ROUGE-2

정답과 예측에 공통으로 나타나는 2-gram의 재현 정도를 평가한다.

## ROUGE-L

두 문장의 최장 공통 부분수열(Longest Common Subsequence)을 이용한다.

## METEOR

정확한 단어 일치뿐 아니라 어간·유의어 등을 더 유연하게 반영한다.

## SBERT Similarity

정답과 예측문을 문장 임베딩으로 바꾸고 의미 유사도를 측정한다.

## Average Ranking

논문 표의 `Average Ranking`은 각 범주에서 비교 방법들의 상대 순위를 평균한 값이다.

- 낮을수록 좋음
- 1.0이면 여러 범주에서 대체로 1위

정확한 동점 처리 방식은 별도로 설명되지 않는다.

# t-SNE 메모리 분석

논문은 링크 생성과 메모리 진화를 적용한 A-MEM 임베딩이 기본 메모리보다 더 뚜렷하게 군집화된다고 설명한다.

```text
Base:
  메모리 임베딩이 넓게 흩어짐

A-MEM:
  관련 메모리가 더 응집된 군집을 형성
```

이는 원문에 키워드·태그·문맥 설명을 추가해 임베딩하기 때문에 자연스럽게 나타날 수 있다.

다만 t-SNE는 시각화 도구일 뿐 다음을 직접 증명하지는 않는다.

- 링크가 사실적으로 정확함
- 메모리 진화가 원본을 왜곡하지 않음
- 군집이 실제 질문답변 성능의 원인임
- 장기적으로 드리프트가 발생하지 않음

추가하면 좋은 정량평가는 다음과 같다.

- 링크 precision·recall
- 동일 주제 군집의 purity
- 상충 기억 분리 정확도
- 시간순 사실 보존율
- 원문 대비 context factuality
- 진화 전후 의미 드리프트
- graph path가 정답 근거를 포함하는 비율
- 인간 평가자의 연결 적절성 점수

## 1. 기반 LLM 의존성

## 2. 텍스트만 평가

현재 실험은 대화 텍스트 중심이다.

이미지·음성·영상·센서 데이터의 기억은 다루지 않는다.

## 3. 메모리 드리프트를 직접 평가하지 않음

논문의 공식 한계에는 기반모델 의존성과 멀티모달 확장이 중심적으로 적혀 있다. 장기간 반복 진화에 따른 사실 왜곡은 중요한 추가 위험이지만 실험으로 검증되지 않았다.

필요한 실험:

```text
원문 사실 보존율
진화 횟수별 factual consistency
잘못된 새 정보 주입 후 복구능력
모순되는 기억의 처리
과거 상태와 현재 상태의 구분
```

## 4. 삭제와 망각 정책 부족

A-MEM은 연결과 진화를 강조하지만 다음 정책은 논문 핵심방법에 없다.

- 오래된 기억 삭제
- 잘못 저장된 기억 철회
- 개인정보 삭제 요청
- 중요도 기반 압축
- 반복 기억 병합 기준
- 링크 수 제한

무한히 기억을 쌓는 시스템은 저장비용뿐 아니라 잘못된 기억의 누적 문제가 생긴다.

## 5. 충돌 해결 규칙 부족

다음 두 메모리가 있을 때 어떤 것을 우선할지 명시적 규칙이 없다.

```text
m1: 사용자는 채식을 한다.
m2: 사용자는 오늘 고기를 먹었다.
```

가능한 해석은 여러 개다.

- 채식을 중단함
- 예외적으로 한 번 먹음
- 다른 사람 이야기임
- 잘못된 기억임

시간, 출처, 화자, 확신도, 사실 상태를 별도 필드로 저장해야 한다.

## 6. provenance가 부족함

자동 생성된 context와 tag가 어느 원문을 근거로 하는지 연결해야 한다.

```json
{
  "claim": "사용자는 사진을 취미로 지속하고 있다.",
  "evidence": [
    {
      "memory_id": "mem-10",
      "span": "I've taken up photography",
      "timestamp": "2023-11-17"
    }
  ]
}
```

## 7. 링크 품질의 직접 평가가 없음

QA 성능은 좋아졌지만 생성된 링크 자체가 정확한지 사람 라벨과 비교하지 않는다.

## 8. 검색 공식과 그림 설명이 완전히 일치하지 않음

본문 수식은 순수 Top-k이고 그림은 연결된 box까지 자동 접근한다고 설명한다.

## 9. k의 테스트범주별 튜닝

범주별 최적 \(k\)를 사용하면 실제 환경에서 질문 유형을 미리 알고 있다는 가정이 들어갈 수 있다.

## 10. 원자적 노트 분할 기준 미제시

한 대화에 여러 사실이 있으면 하나의 노트에 섞일 수 있다.

## 11. 쓰기 비용이 누적됨

검색은 빠르지만 메모리가 추가될 때 LLM 호출이 필요하다. 많은 이벤트가 초당 발생하는 환경에서는 비동기 큐와 배치 처리가 필요하다.

## 12. 개인정보와 보안

장기 메모리는 다음 위험을 가진다.

- 개인정보의 무기한 저장
- 민감정보의 잘못된 연결
- 삭제 후 파생 메모리에 정보가 잔존
- 프롬프트 인젝션이 기억으로 고착
- 악성 메모리가 이웃 메모리를 오염
- 사용자 간 메모리 격리 실패

# 교육용 AI 에이전트 플랫폼에 적용하는 구조

A-MEM을 소그룹 채팅과 미션 피드백 시스템에 적용하면 다음처럼 구성할 수 있다.

```text
그룹 채팅 메시지
  ↓
원자적 사건 추출
  ├─ 학습자가 이해한 개념
  ├─ 반복해서 틀리는 오류
  ├─ 받은 피드백
  ├─ 반영한 피드백
  ├─ 미션 진행상태
  └─ 선호하는 설명방식
  ↓
A-MEM 노트 생성
  ↓
그룹·학습자·미션별 연결
  ↓
기존 학습상태 진화
  ↓
다음 채팅에서 관련 기억 검색
  ↓
개인화된 피드백
```

## 예시

### 첫 번째 기억

```text
사용자:
"리스트 안에 연락처 딕셔너리를 넣는 방식이 맞아?"
```

```json
{
  "context": "학습자가 리스트와 딕셔너리를 조합해 연락처를 저장하는 구조를 확인함",
  "keywords": [
    "Python list",
    "dictionary",
    "contact"
  ],
  "tags": [
    "Python",
    "data structure",
    "contact mission"
  ]
}
```

### 두 번째 기억

```text
사용자:
"피드백을 반영해서 전체 연락처 조회 기능을 추가했어."
```

새 기억은 이전 기억과 다음 관계로 연결된다.

```text
자료구조 설계
  → 피드백 수신
  → 조회 기능 구현
  → 미션 진행
```

기존 메모리의 문맥도 다음처럼 진화할 수 있다.

```text
초기:
"연락처 저장 구조를 설계 중"

진화 후:
"리스트와 딕셔너리 기반 저장 구조를 확정하고 조회 기능까지 구현함"
```

## 그룹별 메모리 격리

A-MEM을 그대로 전체 저장소 하나로 사용하면 다른 강의·그룹의 기억이 섞일 수 있다.

검색 전에 다음 필터가 필요하다.

```python
filters = {
    "tenant_id": current_course_id,
    "group_id": current_group_id,
    "student_id": current_student_id,
}
```

필요에 따라 공유범위를 나눈다.

```text
개인 기억:
  특정 학습자의 진도와 오류

그룹 기억:
  해당 소그룹의 토론과 공동 피드백

강의 기억:
  전체 강의의 공통 개념과 미션 기준

전역 기억:
  재사용 가능한 일반 프로그래밍 지식
```

# 권장 검색 점수

A-MEM의 순수 cosine Top-k를 실제 시스템에 확장하면 다음 점수를 사용할 수 있다.

\[
Score_i
=
w_sS_{\mathrm{semantic}}
+
w_rS_{\mathrm{recency}}
+
w_gS_{\mathrm{graph}}
+
w_pS_{\mathrm{priority}}
+
w_cS_{\mathrm{confidence}}
\]

- \(S_{\mathrm{semantic}}\): 질의와 기억의 의미 유사도
- \(S_{\mathrm{recency}}\): 최근 정보 우대
- \(S_{\mathrm{graph}}\): 관련 seed 기억과의 연결강도
- \(S_{\mathrm{priority}}\): 사용자가 직접 저장하라고 한 중요기억
- \(S_{\mathrm{confidence}}\): 사실 신뢰도

예시 가중치:

\[
Score_i
=
0.50S_{\mathrm{semantic}}
+
0.10S_{\mathrm{recency}}
+
0.20S_{\mathrm{graph}}
+
0.10S_{\mathrm{priority}}
+
0.10S_{\mathrm{confidence}}
\]

이 식은 논문의 공식이 아니라 실무 확장안이다.

# 기억 진화 승인 규칙

모든 후보를 LLM 판단만으로 수정하지 말고 규칙을 추가하는 편이 안전하다.

```python
def can_evolve(old_memory, new_memory, decision) -> bool:
    if decision.confidence < 0.8:
        return False

    if old_memory.source.priority == "user_explicit":
        return False

    if decision.changes_original_content:
        return False

    if decision.is_contradictory:
        return False

    if old_memory.evolution_count >= 5:
        return False

    return True
```

명시적인 모순은 덮어쓰기보다 상태 변화로 저장한다.

```text
old state:
사용자는 서울에 거주

new state:
사용자는 부산으로 이사

처리:
old.valid_to = 이사일
new.valid_from = 이사일
```

# A-MEM과 단순 벡터 RAG 비교 예시

## 단순 벡터 RAG

```text
질문:
"사용자가 사진을 시작한 뒤 여행에서 무엇을 했지?"

검색:
사진과 가장 비슷한 문장 3개
```

사진 메모리와 여행 메모리의 표현이 멀면 둘 중 하나를 놓칠 수 있다.

## A-MEM

```text
사진 취미 메모리
  ├─ 카메라 구매 메모리
  ├─ 여행 메모리
  └─ 야경 촬영 메모리
```

사진 취미를 seed로 찾은 뒤 연결된 여행·촬영 경험까지 따라갈 수 있다.

이 구조가 논문의 Multi-Hop 성능 향상을 설명하는 핵심 가설이다.

# 핵심 결론

A-MEM의 핵심은 기억을 많이 저장하는 것이 아니다.

```text
원문 저장
  + 의미 속성 생성
  + 관련 기억 링크
  + 새 경험에 따른 과거 해석 진화
```

을 결합해 기억 저장소가 스스로 조직되게 하는 것이다.

논문이 보여준 주요 결과는 다음과 같다.

- 6개 기반모델에서 장기 대화기억 성능을 평가했다.
- A-MEM은 특히 Multi-Hop과 Temporal 추론에서 강점을 보였다.
- Link Generation이 기억 네트워크의 기본구조를 만들었다.
- Memory Evolution은 기존 기억의 문맥을 추가로 정제했다.
- 전체 대화를 넣는 방식보다 85~93% 적은 토큰으로 동작했다.
- 벡터 검색 자체는 100만 메모리에서도 빠르게 유지됐다고 보고했다.
- 공식 구현은 ChromaDB와 여러 LLM 백엔드를 지원한다.

하지만 실무적으로는 다음을 반드시 보강해야 한다.

- 원문 불변 보존
- 파생 문맥의 버전관리
- 모순과 시간상태 처리
- 링크 근거와 신뢰도
- 삭제 전파
- 개인정보 격리
- 프롬프트 인젝션 방어
- 메모리 드리프트 측정
- 그래프 확장 검색의 명확한 규칙
- 쓰기·진화 비용 모니터링

따라서 A-MEM은 완성된 인간 기억 모사 시스템이라기보다, **정적인 벡터 저장소를 자기 조직화하는 에이전트 메모리 네트워크로 확장한 아키텍처**로 보는 것이 가장 정확하다.
